# Паспорт пилотного проекта

## Наименование

Пилотный проект по разработке каскадной системы на основе больших языковых моделей для автоматизированной экспресс-оценки стартапов по экспертным критериям.

## Основание проекта

Текущая система оценки проектов, работающая только на промптах, сталкивается с ограничением воспроизводимости: критерии заданы на верхнем уровне, но не разложены на наблюдаемые признаки, из-за чего модель интерпретирует их не по методике экспертного совета, а по собственной скрытой логике.Для задач такого типа более надежным считается подход, в котором отдельно фиксируются признаки, подтверждающие фрагменты текста и правила выставления балла по детализированным рубрикам.

"Рубрика" - условное название одного параметра оценки, например “реальность проблемы”, в котором зафиксированы:
1) критерии параметра
2) наблюдаемые признаки критериев и антипризнаки
3) Шкала оценки единая и описана далее в разделе "Шкала оценки"

Далее в приложениях более подробно это разобрано.

## Цель пилота

Проверить, можно ли без дообучения модели и без отдельной базы знаний, только за счет каскадной схемы обработки, структурированных рубрик, разметки эталонного корпуса и доработки промптов, получить по выбранным параметрам оценки, сопоставимые с экспертной оценкой.

## Гипотеза пилота

Если разложить экспертную методологию на атомарные признаки, зафиксировать шкалу 0–5, потребовать от модели ссылки на подтверждающие фрагменты текста и разделить извлечение оснований и выставление балла на разные шаги (каскадная модель оценки), то качество и воспроизводимость автоматизированной оценки заметно возрастут по сравнению с одноступенчатой оценкой одним промптом.

## Предмет пилота

Объектом оценки является текст проекта в стандартном формате: краткая аннотация, питч-презентация и, при наличии, дополнительные материалы. Пилот не решает задачу финального маршрутизационного «светофора». На этапе пилота проверяется только качество подоценок по отдельным параметрам и качество их объяснения.

## Границы пилота

В пилот включаются три параметра:

+ реальность и обоснованность проблемы
+ рыночный потенциал вне одного заказчика
+ наличие проектного задела.

Параметр _«влияние на технологический суверенитет / критичность технологии»_ выносится за границы первой версии пилота и рассматривается как следующий этап, так как он сильнее зависит от внешней отраслевой рамки и хуже оценивается только по внутреннему тексту проекта.

## Шкала оценки

Для каждого критерия (проблема конкретна, проблема измерима, проблема адресна и т.п.)  используется единая шкала 0-2:

+ 0 — признаки полностью отсутствуют в проекте
+ 1 — признаки формально есть, но не убедительно
+ 2 — признак описан убедительно.

Для каждого параметра используется единая шкала 0–5:

+ 0 — параметр не описан или не поддается оценке по представленным материалам
+ 1 — описание присутствует, но ни один критерий рубрики не выражен
+ 2 — описание присутствует, выражено не менее 1 критериев рубрики
+ 3 — описание присутствует, выражено не менее 2 критериев рубрики
+ 4 — описание присутствует, выражено не менее 3 критериев рубрики
+ 5 — описание присутствует, выражены все 4 критерии рубрики

## Правила выставления балла

- Балл ставится по числу надежно подтвержденных критериев.
- Частичное или слабое упоминание индикатора не считается достаточным подтверждением критерия.
- При наличии выраженных антипризнаков критерий не засчитывается как подтвержденный, даже если в тексте есть отдельные формальные упоминания.
- Если в проекте есть противоречие между описанием проблемы и другими разделами, эксперт вправе не засчитывать соответствующий критерий до устранения противоречия.

## Выборка и эталонный корпус

Для калибровки используется корпус из 15 ранее оцененных проектов. Разметка выполняется двумя экспертами независимо, после чего третий эксперт проводит ревью и фиксирует итоговую эталонную версию.Такой подход нужен для снижения случайности в рубрике и калибровки человеческого согласия до запуска машинной оценки .

Дополнительно формируется отложенная тестовая выборка из 10 новых проектов, не использованных при разработке рубрик и промптов. Наличие отдельной отложенной выборки необходимо, чтобы проверить переносимость методологии на новые кейсы, а не только точность на учебной выборке .

## Методологические принципы

### 1. Разделение фактов и оценки

Система не должна сразу выставлять балл по полному тексту проекта. Сначала она должна извлечь признаки и подтверждающие фрагменты текста, а уже затем интерпретировать их по рубрике и выставлять оценку.

### 2. Оценка с опорой на текстовые основания

Каждый подвывод должен опираться на конкретный фрагмент текста проекта или сопровождаться явным указанием, что подтверждение не найдено - это снижает риск галлюцинаций и делает результат проверяемым.

### 3.Оценивание по рубрикам

Каждый параметр описывается через

1) критерии параметра - оптимально около 4 критериев для каждого параметра оценки,
2) наблюдаемые признаки критериев и антипризнаки,
3) порог подтверждения - для каждого критерия явно зафиксировано условие, при котором формальные или частичные упоминания индикаторов не считаются подтверждением: критерий подтверждается, только если найденные фрагменты закрывают этот порог,
4) шкала - шкала для всех рубрик одинаковая по умолчанию (если не требуется специфический метод расчета оценки).

### 4.Каскадная архитектура

Пилот строится как многошаговая каскадная схема, где извлечение оснований, выставление балла и проверка согласованности выполняются раздельно. Это позволяет локализовать ошибки и сравнивать модели по отдельным функциям, а не только по финальному баллу .

### 5.Проверяемость и воспроизводимость

Приоритет пилота - воспроизводимая и объяснимая оценка, пригодная для дальнейшего масштабирования на остальные критерии и новые проекты.

## Архитектура пилота

### Шаг 1.Нормализация входа

Форматом нормализации проекта является каноническая структура из 9 разделов (Проблема, Решение, Технологическое ядро, Конкуренты и аналоги, Коммерциализация и рынок, Команда и партнеры, Технологическая готовность, Прогресс и планы, Государственная значимость), совпадающая с типовой логикой экспертного скоринга. Все входные документы проекта приводятся к этой единой структуре независимо от исходного формата презентации или описания. Далее для каждого параметра пилота фиксируется карта основных и дополнительных разделов, из которых допускается извлечение оснований для оценки.

Как это выглядит по шагам

1. Система читает аннотацию и все слайды как набор текстовых блоков.
2. Каждый блок сопоставляется с одним или несколькими каноническими разделами: “Проблема”, “Решение”, “Коммерциализация и рынок” и так далее.
3. Если слайд смешанный, он может быть разрезан на части или целиком привязан к нескольким разделам.
4. Если слайд авторский и не вписывается в 9 разделов напрямую, он либо попадает в “дополнительные материалы”, либо его полезные фрагменты распределяются по подходящим разделам.

На выходе должен появиться не список слайдов, а примерно такая структура:

1. Проблема → сюда собраны все фрагменты из аннотации и слайдов, которые описывают боль, потребность, дефицит, носителя проблемы.
2. Решение → сюда собраны фрагменты про продукт, механику решения, способ устранения проблемы.
3. Коммерциализация и рынок → сюда ушли все куски про рынок, клиентов, сегменты, масштабирование, спрос.
4. Прогресс и планы / Технологическая готовность → сюда попали признаки прототипа, MVP, пилота, стадии разработки.
5. Остальные разделы — по той же логике.

### Шаг 2.Извлечение оснований

Языковая модель извлекает по каждому параметру:

- подтверждающие фрагменты текста;
- декомпозиция рубрики (критерии, признаки, антипризнаки)
- отсутствующие данные (чего не найдено для более высокой оценки)
- предварительную уверенность в полноте найденных оснований

На этом шаге балл не выставляется .

### Шаг 3.Выставление балла по рубрике

Отдельный шаг получает только структурированный результат извлечения и выставляет оценку 0–5 по параметру, а также формулирует:

- почему балл не выше;
- почему балл не ниже;

Разделение извлечения оснований и выставления балла уменьшает смешение фактов и интерпретации .

### Шаг 4.Проверка согласованности

Финальный шаг проверяет:

- соответствует ли выставленный балл найденным подтверждающим фрагментам текста;
- нет ли ссылок на отсутствующие в проекте факты;
- нет ли логических противоречий между объяснением и найденными основаниями.

### Формат результата системы

Для каждого параметра система должна возвращать структурированный JSON с полями:

- parameter\_name - название оцениваемого параметра, например: «реальность проблемы» или «наличие проектного задела» и т.п.
- score - итоговый балл по параметру по шкале от 0 до 5, выставленный на основе найденных признаков и рубрики 
- evidence\_spans - список подтверждающих фрагментов текста проекта, на которые система опирается при оценке
- observed\_signs - наблюдаемые признаки (из рубрики)
- anti\_signs - наблюдаемые антипризнаки (из рубрики)
- missing\_data - то, чего в проекте не хватает для повышенной оценки (не выраженные критерии)
- why\_not\_lower - пояснение, какие найденные основания не позволяют занизить оценку и удерживают ее хотя бы на текущем уровне - опционально.
- confidence - уровень уверенности системы в своей оценке с учетом полноты данных, качества найденных оснований (техническое поле)

Структурированный формат ответа повышает трассируемость и облегчает последующее сравнение моделей и кейсов.

## Работы по пилоту

### Блок 1.Подготовка корпуса

1. Сформировать список из 25 проектов для калибровочной выборки.
2. Собрать по каждому проекту комплект материалов: аннотация, презентация, дополнительные материалы при наличии.
3. Подготовить отдельную отложенную выборку новых проектов для тестирования переноса методологии.

### Блок 2.Разработка методологии версии 1

1. Зафиксировать три пилотных параметра.
2. Для каждого параметра описать рубрику: признаки, уровни качества, антипризнаки, отсутствующие данные, типовые вопросы к проекту.
3. Подготовить якорные примеры сильного, среднего и слабого описания для каждого параметра.

Для каждого параметра описывается рубрика, то есть практическая схема оценивания: какие наблюдаемые признаки подтверждают сильную или слабую проработку параметра, какие маркеры снижают оценку, каких данных не хватает для уверенного вывода и какие типовые вопросы должен задать эксперт или система при анализе проекта. В приложении №1 описан практический пример того, как может выглядеть рубрика на примере одного параметра

### Блок 3.Экспертная разметка

1. Провести независимую разметку корпуса двумя экспертами.
2. Зафиксировать по каждому проекту балл, подтверждающие фрагменты текста и объяснение оценки.
3. Провести ревью третьим экспертом.
4. Собрать итоговую эталонную размеченную выборку для пилота.

В приложении №2 описан практический пример того, как может выглядеть типичная разметка

### Блок 4.Проектирование каскадной схемы

1. Описать схему нормализации проектных документов.
2. Подготовить JSON-схему результата.
3. Разработать промпты для извлечения оснований, выставления балла и проверки согласованности.
4. Настроить журналирование промежуточных результатов по каждому шагу.

### Блок 5.Прогоны и сравнение моделей

1. Прогнать эталонную размеченную выборку через несколько языковых моделей.
2. Сравнить совпадение подоценок (оценок отдельных параметров) с эталонной разметкой.
3. Сравнить качество подтверждающих фрагментов текста и объяснений.
4. Зафиксировать типовые ошибки каждой модели .

### Блок 6.Анализ расхождений

1. Выделить случаи завышения оценки.
2. Выделить случаи занижения оценки.
3. Отдельно разобрать ложную конкретику, пропуск важных признаков и опору на стилистически сильный, но содержательно пустой текст .
4. На основе анализа подготовить вторую версию рубрик и промптов.

### Артефакты пилота

По итогам пилота должны быть подготовлены следующие артефакты:

+ рубрики версии 1 по трем параметрам;
+ эталонная размеченная выборка;
+ JSON-схема результата;
+ набор промптов для извлечения оснований, выставления балла и проверки согласованности;
+ таблица сравнения «эксперт — языковая модель»;
+ карта ошибок;
+ рубрики и промпты версии 2.

### Критерии успешности

Пилот считается успешным при одновременном выполнении трех условий:

1. Система показывает приемлемое совпадение подоценок с экспертной разметкой на учебной и тестовой выборках.
2. Система предъявляет корректные текстовые основания для выставленных баллов.
3. Методология переносится на новые проекты без существенного падения качества .

Финальная оценка успешности должна проводиться не только по совпадению балла, но и по совпадению причин и качеству подтверждающих фрагментов текста, поскольку для объяснимых систем это критично не меньше, чем само числовое совпадение.

### Решение по итогам пилота

По итогам пилота принимается одно из трех решений:

- масштабировать методологию на остальные параметры оценки;
- провести еще одну итерацию на тех же трех параметрах с доработкой рубрик и промптов;
- признать, что для части параметров подхода только на промптах недостаточно и требуется усиление через дополнительные правила, внешние источники или дообучение.

### Ожидаемый эффект

В случае успешного пилота проект получает основу для перехода от узкого экспертного места к воспроизводимому конвейеру первичной оценки, в котором человек сохраняет контроль над маршрутизацией и спорными случаями, а языковая модель берет на себя массовую предварительную экспертизу по формализованной методике.
